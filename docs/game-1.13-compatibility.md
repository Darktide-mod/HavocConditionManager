## Prepared changes and source evidence

- The difficulty picker resolves `DangerSettings.danger_levels`, retaining the old flat-table fallback. Native `scripts/settings/difficulty/danger_settings.lua` now returns a wrapper. Before edits, the real current data with mocked UI boundaries reproduced `stepper_templates.lua:94: attempt to index local 'danger_settings' (a nil value)`.
- The roamer constructor forwards all trailing arguments and native returns. Current `roamer_pacing.lua` accepts `optional_forced_sub_faction`; `pacing_manager.lua` supplies the mission override both during construction and template replacement.
- DIY update registration uses the modern `(unit, "update")` interface when `_disable_reasons` identifies the new native system, otherwise retains the legacy class/unit interface. `extension_system_base.lua:188–221` resolves the extension through its unit and keeps disable reasons separately. HCM releases/restores the native default reason and leaves independent pause reasons in place; native buffs can still resume an empty extension later.
- Constructor timing is handled explicitly. Native `on_add_extension` constructs the minion before filling its map (`extension_system_base.lua:94–113`). Modern registration is deferred until that method completes; the `MinionBuff.init` callback retains the legacy behavior. The post-construction callback runs before unit-registration events, so a first proc request need not wait for a DIY tick. A post-`register_extension_update` callback reconciles the native default reason even when HCM has already marked the minion enabled: a separate pause can remove its update-list entry before registration, causing native registration to add that default reason again. HCM removes only the default reason, preserving independent pauses until their owner resumes. Cleanup requires the map to still identify the owned extension and cannot disable a replacement mapped to the same unit.
- `ability_cooldown` retains the old cooldown API when present. Current `player_unit_ability_extension.lua` removed it in favor of resource consumers (`:1037`, `:1127`). Fractions restore one charge's cost for charged pools, or a fraction of maximum resource for continuous pools. Absolute/event-damage values remain seconds, converted through the configured base flat plus percentage regeneration rate. Regeneration-speed buffs do not change that conversion; native restoration/consumption APIs apply their own stat modifiers, clamping, charge reconciliation and proc effects. Disabled/missing and inventory-only abilities are rejected; fully ready abilities retain the legacy early-out, including negative adjustments. Grenade actions retain whole-charge semantics.

The resource adapter intentionally uses native resource operations rather than editing network component values. Positive restoration follows the requested ability's native pool override; negative consumption targets that resolved pool. Tests cover a shared pool with compatible per-charge costs; arbitrary cross-pool cost mismatches have not been verified.

The public DIY schema supports cooldown amounts of kind `flat`/`fraction` and rejects negative and event-damage cooldown actions. The ability helper also directly tests private adapter boundaries (using `absolute` for the generic non-fraction branch); its negative/event-damage cases do not establish that those inputs can pass schema validation or persisted-package loading. The schema was not broadened. After runtime approval, the helper gained actual native RGB/alpha assertions, a supported `flat` cooldown case, native consumption-modifier assertions and regeneration-speed non-interference checks; these pass.

## Replacement/readiness draft added in the bounded follow-up

Deferred monster processing remains in native `on_spawn_points_generated`, which clears the pending root before its one native application (`pacing_manager.lua:133–151`). No native template/global table is rewritten.

Mutator readiness: HCM's deduplicating loader calls native `load_mutator_from_name`, which activates unconditionally when `activate_on_load` is set (`mutator_manager.lua:145–164`). Native `_load_mutators` now waits for `is_loading_done`. Completion is already supported: `GameplayInitStepManagers.update` polls `MutatorManager.is_loading` before advancing initialization (`gameplay_init_step_managers.lua:64–76`); `MutatorBase.is_loading` waits for required packages, activates an `activate_on_load` instance once and sets `_is_loaded` (`mutator_base.lua:59–82`). The draft gates activation only while HCM calls the single loader for that same instance/name; the temporary scope is restored even if construction raises, and the error is rethrown. Other native activation calls and old versions without `is_loading_done` retain their behavior. Existing instances are reused on repeat loads. HCM-owned stim listener records retain their original event manager; preexisting foreign instances are not newly claimed. Deferred spawn callbacks and native update order are unchanged.
